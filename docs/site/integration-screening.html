Integration notes: Payment screening

Working notes on the Intercepta payment-screening integration: where it is called, what the docs told us, and what live use shows.

The provider is called from the payer before signing and again by the resource server before settlement. Credentials stay outside the repository.

Which files call the API

  • app/screening/intercepta.py: the only HTTP client (Quick Scan and Deep Scan Address, Scan Token, Scan Message).
  • app/screening/service.py: decides which calls each hop needs, maps Sepolia addresses to mainnet and stores the verdict.
  • app/screening/policy.py: turns provider responses into PAY / CAP / ASK_HUMAN / REFUSE.
  • app/screening/presign.py: payer-side gate used by the x402 signer hook.
  • scripts/intercepta_x402_smoke.py: 402 → three live scans → sign → retry demonstration.

Tests use fixtures shaped like the provider's OpenAPI reference and never reach the network.

What we learned from the docs

  • Mainnet-only data. Risk data covers mainnet, while our payments settle on Sepolia. Each Sepolia payee is screened as a mapped mainnet address (agents.screening_address, else SCREENING_ADDRESS_MAP). An unmapped payee is refused.
  • riskGroup values. Scan Message returns Low, Medium or High. We map High to ASK_HUMAN and Medium to CAP; drainer or malicious detectors refuse.
  • No score threshold is published. Traits drive our decisions; the toxic-score thresholds (refuse ≥ 80, ask ≥ 60, cap ≥ 30) are our own and configurable.
  • Fail closed. No key, timeout (4 s by default), non-2xx status or an unexpected body all mean REFUSE.

Live observations

  • During local validation, Quick Scan reached the live API and returned HTTP 403 before a verdict was produced.
  • The provider response was {"status":403,"response":"This authentication key is incorrect or doesn’t exist"}.
  • The client records method, endpoint, status, latency and a bounded response body, while never logging the API key.
  • Because the credential was rejected, the application translated the result to HTTP_ERROR and fail-closed REFUSE; no payment was signed.

Friction points and missing capabilities

  • No testnet coverage, so a mapping layer is needed for any Sepolia product.
  • No published guidance on how to turn a toxic score into a decision.
  • A valid sandbox credential is still required to capture an allowed verdict and a successful paid retry.

Top improvement

The largest integration improvement would be documented test addresses or testnet risk data. Until then, explicit mainnet screening-address mappings keep Sepolia settlement from being mistaken for provider-supported testnet risk data.
